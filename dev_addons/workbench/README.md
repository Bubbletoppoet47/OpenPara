# Workbench (workshopping)

A project schematic in the style of ANSYS Workbench, as the first tab of Full dev mode. ONE project file (`.opara`, plain JSON) holds blocks on a canvas; each block is a part, an assembly, an analysis or one of the other tools, with cells (Geometry, Setup, Solution, Results ...) and a status mark on every cell: up to date, incomplete, refresh needed, update needed, failed. Wires join a cell that provides something (the geometry of a part) to a cell that takes it (the geometry of an analysis). Blocks snap to a 20-unit grid, a box selects several, a selection moves as one and the wires follow. Double-click a cell and its usual editor opens in a tab; what is done in the tab is read back into the project when you save it, come back to the Workbench, or press Update.

**Results, meshes and parametric outputs are not saved.** The project keeps what a person typed (the part, the supports, the loads, the mesh size ...). Opening a project never computes anything: the cells say "update" until you press Update Project. Files are kept inside the project, not as links to other folders; the one exception is the Annotator block, whose dataset is too big and stays in its own folder (the block keeps the link).

## The blocks

| Block | What it keeps | Editor |
|---|---|---|
| Part | the part (`.gpd` content) | the part window |
| Assembly | the assembly with its OWN COPY of every component (no live link to the Part blocks; Insert Component can copy from the project's parts) | the assembly window |
| 3D Static Structural, 3D Thermal, 3D Fluid Flow | the analysis project folder without meshes and results (3D Fluid Flow takes one Part, not an Assembly; its Setup is offered to Coupled Physics) | the 3D window |
| 2D Static Structural, 2D Fluid Flow, 2D Thermal, 1D Beam / Truss | the same | the 2D / 1D window |
| Coupled Physics | a heat analysis and a stress analysis of the same geometry (both 2D or both 3D), solved together; the project folder holds the options only | the Coupled Physics window (`dev_addons/coupled`) |
| Sheets, Systems and Controls, Circuits | the document (`.opsheet`, `.opctl`, `.opcirc`) | the tool's tab |
| Truss Generator | the project folder (`project.json`, the sketch) | the Truss tab |
| PDF Editor (no wires) | a folder of the PDFs and page projects (`.oppb`) that are open in it: a PDF opened from anywhere else is COPIED into it (the original is never changed; one copy however often it is opened; past 150 MB of PDFs a file opens where it is and is not kept), a new page project has its file in the folder from the start and names its PDFs relative to itself | the PDF editor tab |
| Annotator (wires out: Dataset, Distances) | a LINK to the annotator project folder (`{"abs", "rel"}`), never a copy: a dataset is photos and video frames. A new block starts on a project in a temporary folder, as the annotator does on its own; when the project is saved to a folder (File > Save in the window) the block takes that folder, and follows the window after Save As. Importing or boxing pictures is a change of the cell; a folder that moved is asked for. Save this system on its own copies the folder | the annotator tab |
| Trainer (wires in: Dataset, Distances; wire out: Models) | the settings of its training project and every model it trained. A model up to **500 MB** is kept INSIDE the `.opara` (one project file is one training); a bigger one is LINKED (written to a `<project> models` folder next to the project file, and said). Never kept in the file: the pictures, the distorted copies, the frozen copies of runs. **Refresh** of its Dataset / Distances cells copies the wired Annotator's pictures, boxes and distances into the block's own training project (same merge as the Trainer's Import dataset zip: newest edit wins); opening the block does that too when the project was just opened. **Update Project never trains**: Training is a data cell (ready once a model exists) and training starts only with Start training in the window. One Annotator for each Trainer | the Trainer tab |
| Trained models (wires in: From trainers, any number; wire out: Models) | ONE list of every model: the ones trained in the Trainers wired into it (they stay in their Trainer: the list follows the wires, nothing is copied), the ones imported into the block (a model file, a folder of them, or dropped on the window: up to **500 MB** each INSIDE the `.opara`, a bigger one LINKED and said), and the ones in the shared Models folder of the Annotator (downloaded from GitHub; listed, never copied into a project). The window has the Annotator's look: ribbon (Import model, Import folder, Export, Rename, Remove), a sheet of details on the left, the list on the right (sort by any heading; **Show: All / Embedded / GitHub models**), a status bar. Export writes the `.pt` with its `.json` beside it. Only a model imported into the block can be renamed or removed; GitHub models and a Trainer's models are changed where they are. A change in the list grows the Library's stamp, so what is wired downstream says refresh. Nothing is trained and no model file is loaded (a `.pt` can run code when it is loaded: the person is asked before one is imported) **Distance-only models** (the Trainer's formula, regressors and networks: one `.opdm` file each, plain numbers; they find no boxes, so a Model testing block tries them on the boxes of a detector) are listed as *Distance only*, kept inside the `.opara` like the others (as readable text), imported / dropped / exported as `.opdm` without the question about code (a pickle-holding boosting model asks when it is opened). Model testing lists them too. | the Trained models tab |
| Model testing (wire in: Models, any number) | the Annotator's **Analyse tab as a block of its own**: open a recorded session of the Gimble rig, run a model over it and see how its distance holds up against the LiDAR frame by frame (confidence, tolerance, closest / median / average, boxes, frames, CSV, report, the made-up example and self-check). The models are those of the Trainers / Trained models blocks wired into its Models cell (nothing is copied) and the ones dropped or imported on the block itself (up to 500 MB each inside the `.opara`, linked above that). Kept in the file: the models, a LINK to the session folder (frames and depth are never copied) and the settings. **Results are not saved**: after the file is opened Analysis says incomplete until Run analysis is pressed. **Analysis is a data cell, not a compute cell: Update Project never runs a model.** Model files or a session folder dropped on the window are taken. The Annotator's own Analyse tab is still there and unchanged (it goes when this block is trusted). **Distance-only models** (`.opdm`) are in the list as *(distance only)*: they find no boxes, so the **Boxes from** box over the setup card names the model that does (any model of the list that is not distance only, or the example's made-up one), the detector runs once over the session whatever number of distance models are tried on its boxes, and the metres of every box come from the distance model; a gradient boosting file holds a pickle and is opened only after a question (remembered while the window is open). Every run made in the window is kept in memory and **Compare models** (it opens by itself at the second run) shows them **side by side**: one row each (boxes judged, share that pass, median and mean distance off, as the Analyse tab judges), a chart of the share that pass in the six LiDAR distance bands (a colour and a marker shape for each run, a hollow marker where fewer than five boxes were judged, a hover says what is behind a point), *Run the other distance models* and *Export CSV*. A run read with the other part of the box ("middle 60 %") says to run again. The choice of detector is kept in the project; the runs are not (as with results) | the Model testing tab |

Wire a Part or Assembly block into an analysis: its Geometry cell says **refresh** whenever the part changes, and Refresh copies the part into the analysis (an assembly's copies are written as plain files first). Opening an analysis block (double-click on any of its cells) does that Refresh for you when the part changed since the block took it: only the geometry is brought up to date, the solve is never run (the Solution cell says **update** until you run it), and a refresh that fails leaves the block as it was and says why. A 2D analysis gets the part and you choose the sketch in its tab; a Refresh takes the same sketch again and keeps the supports and loads of a 2D Static Structural analysis that still fit.

Not wired yet (listed in the toolbox as "Not wired"): Visualize, Motor. The PDF Editor is a block with no wires in or out. The Annotator gives its Dataset and its Distances to a Trainer (one Annotator for each Trainer): a change in the pictures or boxes makes both Trainer cells say **refresh**, a distance picked makes only the Distances cell say it. A Coupled Physics block takes the Setup cells of one Thermal and one Static Structural block (same dimension, same Part or Assembly) in its Physics cell: Update solves the heat analysis, hands its temperature to the stress analysis and solves that; it can also take one Fluid Flow block of the same dimension, 2D or 3D (heat exchange with the solid, pressure on the stress analysis, and, when ticked, the structure moving the flow). **2D analyses wired into a Coupled Physics block have no tab of their own**: a double-click on one of them (any cell) opens the window of the block on that analysis's button of a strip (Fluid, Thermal, Structural, Coupled, Viz), the status line says so, and the Workbench keeps a record of which window holds which analysis (`hosted`). Take the wire out and the analysis is saved and opens as a tab of its own; wire it in again and the tab goes and it moves in; closing the window saves the analyses and shuts them down (their solutions say update). What a Parametric Study or a multi-case block asks for (the editor of an analysis) is the one in the window. **3D analyses keep their own tabs** (moving OpenGL views into the window was not done: OpenGL cannot be drawn where this was built). See `dev_addons/coupled/README.md` for the window, the handed-over rows and the Viz tab. Only tried in a headless Qt, never seen on Windows.

## Buttons

- **Refresh Project**: copies the geometry again into every analysis whose part changed.
- **Update Project**: Refresh, then solve what is out of date, in the order of the wires. A cell that cannot be done says why.
- **Import...** / **Import Folder...**: a `.gpd` part, a `.gpa` assembly (its part files are read into it), an analysis folder (`.gpv .gpf ...`), `.opsheet .opctl .opcirc`, a `.truss` folder, or another `.opara` (its blocks are added next to the ones here).
- **A STEP file** (`.step`, `.stp`) or an **STL file** (`.stl`) can be dropped on the canvas, or taken by Import. A STEP file with one solid is a Part block. With several solids it asks each time: **one Assembly block** (a fixed component for each solid), **one Part block per solid**, or **one Part block with all the solids**. An STL becomes a **mesh body**: a Part block whose one feature is the imported body and keeps only the **triangles** (compact: about 240 KB for 32 000 triangles). The part's solid, one flat face for every triangle however many there are, is made from them whenever the part is built, and kept while the program runs (an STL has no units: they are taken as mm). Its surface must be closed; the usual faults (points that coincide, triangles the wrong way round, small holes) are repaired first and said; one that is still open is refused with the reason. **Making the solid is slow:** about 20 seconds for 32 000 triangles on the machine it was tried on, and more than that for larger meshes (a second time costs nothing in the same session; the first build after the program is started costs it again). Both kinds of block wire into an analysis, a drawing or an assembly like any other part, and open in the part window (a sketch and a cut work on a mesh body; a fillet does not, it has flat faces only). The Visualize node takes its input by a wire when VIS-1 is built.
- Right-click a block: **Save this system on its own...** writes the block as the ordinary file or folder it was (`.gpd`, `.gpa`, `.gpv` ...), which opens in the program like any other.
- **Load Example Project**: a bar, a plate and a frame with three analyses (3D structural, 2D structural, 3D thermal), one analysis deliberately left without a setup, a heated bar (**Bar heating**, **Bar growth**, **Bar thermal stress**: a Coupled Physics block whose known answer, the far end of the bar growing 0.048 mm, is checked and shown as PASS or FAIL), a 20 mm square in slow air (**Square**, **Air flow**, **Square heat**, **Square bending**, **Air, heat and bending**: the flow, the heat exchange and the bending of the square in one Coupled Physics block, the structure moving the flow, with a known answer of walls at 50 degC), a 30 mm copper block in 3D air (**Block**, **Block air flow**, **Block heat**, **Block pressure**, **Air, heat and pressure 3D**: the same three in 3D, with a known answer of walls at 70 degC; two soft checks of the flow, its energy balance and its temperature range, are expected to show FAIL on its coarse mesh and say so), a parametric study and three tools. Press Update Project to solve them.
- **Project Report**: every block and cell with its status, what Update would do, what is incomplete and why, and which editors are open.

## Files

`wb_project.py` (the project, its cells and their statuses, the file; no Qt), `wb_canvas.py` (the schematic), `wb_tab.py` (the tab, toolbar, toolbox, menus), `wb_nodes.py` (what each kind of block does), `wb_parts.py` (Part and Assembly), `wb_analysis.py` (the analyses), `wb_tools.py` (Sheets, Controls, Circuits, Truss, Drawing, PDF Editor, Annotator), `wb_trainer.py` (Trainer), `wb_models.py` (where models are kept and how a block finds them), `wb_models_block.py` + `wb_models_tab.py` (Trained models and its window), `wb_testing.py` + `wb_testing_tab.py` (Model testing and its window), `wb_testing_boxes.py` (a distance-only model on the boxes of a detector; the numbers of a run; no Qt) and `wb_testing_compare.py` (the side-by-side table and chart), `wb_import.py`, `wb_example.py`, `wb_icons.py`, `wb_ext.py`.
Tests (repository root): `test_wb_project.py`, `test_wb_canvas.py`, `test_wb_shell.py`, `test_wb_parts.py`, `test_wb_analysis.py`, `test_wb_2d.py`, `test_wb_tools.py`, `test_wb_drawing.py`, `test_wb_import.py`, `test_wb_example.py`, `test_wb_fluid3d.py`, `test_wb_coupled_flow.py`, `test_coupled_link.py`, `test_wb_coupled_flow3d.py`, `test_wb_pdf_annotator.py`, `test_wb_trainer.py`, `test_wb_models.py`, `test_wb_distance_models.py`, `test_wb_testing_boxes.py`, `test_wb_testing.py`, `test_asm_embed.py`.

Nothing here has been tried on real Windows: everything so far ran headless. The OpenGL views cannot draw there, so how the editors look inside the tabs has not been seen.
- **Layout**: blocks never overlap and keep a gap of 40 (a dragged block stops at its neighbour and slides along it; a new block goes to the nearest free place; a file from before the rule is moved apart when opened). Wires are horizontal and vertical pieces that run round the blocks (`wb_route.py`), never behind them.
- **Study -> Sheets**: the Results cell of a Parametric Study can be wired into the Study Results cell of a Sheets block. In that block's Sheets window, Data > Import study offers only the wired studies; Refresh / Update Project reads the imported tables again.
- **Drawing block** (Component Tools): its Models cell takes Part / Assembly blocks by wire; Open Drawing shows the sheet, model and projected views, a scale and a display style for each view, dimensions (you pick the type first: Horizontal, Vertical, Length / distance, Diameter, Radius, Angle; always the model's true values), center marks, centerlines, notes (text, size, straight or bent leader), balloons, lines / rectangles / circles / arcs drawn on the sheet, and PDF export (`dev_addons/drawings`). Refresh / Update Project re-projects the views from the wired models and says which ones could not be rebuilt.
